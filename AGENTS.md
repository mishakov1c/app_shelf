# Правила работы с AppShelf

## Репозиторий и объём изменений

- Работай в текущем клоне репозитория AppShelf; не создавай отдельные копии, временные репозитории или worktree без явной необходимости.
- Перед изменениями изучи текущую реализацию, состояние рабочего дерева и связанную документацию. Сохраняй чужие незакоммиченные изменения.
- Не реализовывай новые функции и не меняй архитектуру без согласования. `ROADMAP.md` описывает планы, а не разрешение начать разработку.
- Проект собирается как .NET Framework WPF через `Build-AppShelf.cmd`; `AppShelf.csproj` также поддерживает публикацию .NET 8. Не переводи проект на другую платформу без отдельного согласования.

## Пользовательские данные и совместимость

- Сохраняй совместимость с существующими `apps.json`, `reminders.json` и собственными ярлыками AppShelf. Изменения формата должны предусматривать безопасную миграцию прежних данных.
- Не удаляй и не перезаписывай пользовательские данные при обновлении или сборке.
- Не добавляй в Git содержимое `%APPDATA%\AppShelf`, резервные копии, ярлыки пользователя, кеши, журналы, API-ключи, токены, `.env` и другие секреты.
- Не публикуй экспортированные архивы: они могут содержать список программ и персональные пути.

## Git и GitHub

- Не меняй глобальную Git-конфигурацию.
- Для GitHub используй только локальную идентичность репозитория:
  - `user.name`: `mishakov1c`;
  - `user.email`: `26500318+mishakov1c@users.noreply.github.com`.
- Перед коммитом проверяй `git var GIT_AUTHOR_IDENT`, `git var GIT_COMMITTER_IDENT` и переменные окружения `GIT_AUTHOR_*` / `GIT_COMMITTER_*`. Корпоративная почта не должна попадать в историю.
- Проверяй фактические автора и коммиттера после коммита. До отправки проверяй состав файлов и отсутствие секретов.
- Не выполняй force-push и не переписывай опубликованную историю. Перед интеграцией изучай существующие удалённые коммиты.

## Сборка, проверка и релизы

- Для обычной сборки Windows используй `Build-AppShelf.cmd`; для автоматической сборки без GUI и пауз — `Build-AppShelf.cmd --no-start --no-pause`.
- Не выдавай статический анализ за успешную компиляцию или пользовательское тестирование. Явно указывай, что именно проверено.
- GitHub Actions должен завершаться ошибкой при неуспешной сборке. В artifact передавай только собранное приложение, без пользовательских настроек и секретов.
- Не публикуй Release при неуспешной сборке. Не создавай Release автоматически на каждый коммит.
- Release должен содержать готовое Windows-приложение. Создавай и публикуй тег только для версии, готовой к выпуску; для первого релиза дополнительно требуется пользовательское тестирование EXE.

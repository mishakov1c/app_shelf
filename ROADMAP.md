# План развития AppShelf

**Актуализировано: 24.11.2026. Последний стабильный выпуск — 2.22.0. Разрабатывается 2.23.0: автоматические резервные копии и резервирование перед обновлением; согласовано отдельное дополнение — канал бета-версий. Аварийный откат обновления отдельно не проверялся.**

Здесь находятся незавершённые задачи, согласованные будущие возможности, расследования, отдельные проверки и контекст принятых решений. Выпущенные функции не дублируются как открытые задачи; их история — в [CHANGELOG.md](CHANGELOG.md). Открытый пункт **не разрешает начинать разработку без отдельного согласования**.

Статусы: **[ ]** — ещё не сделано / не проверено в требуемых условиях; **отложено** — согласованная идея без срока. Успех автоматических WPF-тестов не заменяет проверку на реальном Windows DPI.

## AppShelf 2.23.0 — автоматическое резервное копирование (24.11.2026)

- [ ] **Единая выбранная папка:** автоматические архивы, копии перед обновлением и страховочные копии восстановления сохранять в явно указанной пользователем папке (включая каталоги Dropbox/OneDrive). Не разрешать папку данных AppShelf, папку EXE и их родительские каталоги. Ручной экспорт по умолчанию предлагать в подпапке `Manual`.
- [ ] **Автоматические ZIP:** раз в сутки по умолчанию, опция раз в неделю; фоновое выполнение после запуска и при длительной работе, без создания одинаковых ZIP при неизменных данных и без задержки закрытия. Опции 3/7/14 архивов и лимит 512 МБ / 1 / 2 / 4 ГБ (по умолчанию 7 и 1 ГБ); оставлять хотя бы одну копию каждого типа и не чистить ручные/страховочные архивы.
- [ ] **Перед обновлением:** после проверенной загрузки, до старта установщика создавать проверенный полный ZIP и копию текущего EXE в `BeforeUpdate`; не более трёх комплектов. Ошибка бэкапа блокирует установку, пока пользователь явно не выберет «Повторить» или «Установить без копии». Штатная замена EXE не должна оставлять новые постоянные `.previous` рядом с программой; для аварийного отката сохраняется временный исполняемый файл установщика.
- [ ] **Переход со старого обновлятора:** старый 2.22.0 ещё может оставить `.previous` при установке 2.23.0. После выбора каталога копий перенести этот файл в `BeforeUpdate` и удалить исходный только после сверки хеша. Ручные архивы и чужие файлы не удалять.
- [ ] **Безопасность данных:** переиспользовать проверяемый ZIP, не экспортировать персональный путь бэкапов, проверять неизменность исходных данных на протяжении операции; успешная запись ZIP на локальный диск не означает завершение синхронизации облачного клиента.
- [ ] **Восстановление:** страховочные копии перед восстановлением сохранять в выбранном каталоге; после подтверждённого импорта AppShelf должен завершаться, а не скрываться в трей.
- [ ] **Проверки:** отдельные сценарии сохранения, сроков хранения, отказов файловой системы, копирования EXE и миграции; штатная Windows-сборка и полная регрессия. Ручная проверка интерфейса и облачной папки — до объединения PR.
- **Не включать:** переключение обоев Windows, PocketHub, профили, локализацию и прочие доработки. Обои Windows перенесены в самый конец бэклога, срок не назначен. Бета-канал согласован как отдельное дополнение к 2.23.0; остальные предложения отложены.

### Канал бета-версий — дополнение к 2.23.0 (24.11.2026)

**Согласованная идея пользователя:** быстро проверять новые функции на реальном ПК, устанавливая бета-сборки непосредственно через встроенное обновление, без ожидания отдельной локальной проверки агентом. Реализацию вести отдельной задачей; текущий PR резервного копирования не считать реализацией бета-канала. Разработка начата 24.11.2026 в `feature/beta-update-channel-2.23.0` от ветки резервного копирования. Сборка, автоматические проверки и ручная приёмка ещё не подтверждены.

- [ ] В настройках обновления добавить флажок **«Проверять бета-версии»**, по умолчанию выключен (включая существующие настройки при отсутствии нового поля). При выключенном флажке предлагать только стабильные выпуски; при включённом — более новые стабильные и бета-выпуски.
- [ ] Бета-релизы содержат экспериментальные функции, ещё не принятые пользователем; публиковать их как GitHub Releases с признаком `prerelease`, отдельными тегами наподобие `2.24.0-beta.1` и понятным обозначением «Бета» в интерфейсе и заметках выпуска. Не выдавать бету за стабильную версию и не заменять ею последний стабильный выпуск.
- [ ] Для публикации беты достаточно успешной штатной Windows-сборки и автоматических проверок GitHub Actions; отдельный локальный прогон через OpenCode не является обязательным предварительным этапом. Бету можно собирать из функциональной ветки без объединения непроверенной функции с `main`. Пользователь обновляется на неё и вручную проверяет новую функцию; стабильный выпуск — только после приёмки по действующим правилам.
- [ ] При выборе обновления корректно сравнивать стабильные и предварительные версии (в частности, beta.10 новее beta.2, а финальная версия новее своих бет); исключать черновики и случайное понижение версии. Отключение бета-канала не должно автоматически откатывать приложение. Переход с беты на более новую стабильную версию — штатный сценарий; способ явного возврата на предыдущую стабильную версию проработать отдельно.
- [ ] Переиспользовать проверку скачанного EXE, резервирование данных и старого EXE перед установкой, существующие меры безопасности обновлятора. Согласовать представление SemVer в метаданных Windows EXE и первый переход со старого обновлятора, который не видит бета-релизы.
- [ ] Проверить в CI фильтрацию каналов, миграцию настройки, сортировку версий, переход beta → beta и beta → stable, изоляцию стабильного workflow и запрет публикации при неуспешных проверках. Автоматический фоновый поиск обновлений — отдельная отложенная идея, не часть этого решения.

### PocketHub — главное мобильное направление, начало работ

- [ ] **Разработать PocketHub — отдельное мобильное приложение (репозиторий `mishakov1c/PocketHub`), в перспективе связанное с настольным AppShelf.** Это не перенос Windows-лаунчера на телефон. Первый этап — только напоминания.
- **Текущий объём:** на первом этапе разрабатывать только модуль напоминаний (список, создание/редактирование, повторения, локальные уведомления); точные сценарии уточнять до реализации. Таймеры, Помодоро и остальные модули сейчас не разрабатывать.
- **Связь с настольной версией обязательна как цель:** данные и работа мобильного приложения должны быть связаны/синхронизированы с AppShelf на ПК. Способ синхронизации и необходимость облака пока **не определены** — решить отдельно до разработки.
- **Совместимость повторов:** перед будущей синхронизацией PocketHub должен поддержать уже выпущенные в AppShelf режимы `weekdays`, `weekends` и `custom_weekdays` с маской `repeatWeekdays` (Пн–Вс, биты 0–6). Пока это отложенная Android-доработка, не считать её реализованной.
- **Технологии (решение от 16.11.2026):** для первой версии Android выбран **Kotlin + Jetpack Compose**. iOS по-прежнему в бэклоге. Не определены архитектура синхронизации, сроки её появления и детали мобильных уведомлений.
- **Платформы (решение от 16.11.2026):** первая версия PocketHub — только Android. iOS — отдельная задача в бэклоге без сроков; не реализовывать сейчас. Учитывать возможную поддержку iOS при проектировании, но не делать её обязательным условием для первого Android-релиза.
- **Статус:** каркас и CRUD-напоминания с Room уже объединены в `main`, пользователь подтвердил локальное сохранение данных на телефоне. Системные уведомления подготовлены в `feature/android-reminder-notifications` / PR #5, но не приняты и не объединены. К этому этапу вернуться только после отдельного решения.

### Универсальный модуль «Подборки» — выпущен в 2.17.0, дальнейшие расширения отдельно

- [x] **Реализовать независимые пользовательские подборки любой тематики.** «Что приготовить?» становится одним из вариантов использования, а не названием и ограничением модуля. Можно создавать любое число подборок: рецепты, кино, игры, книги, места, занятия и свои произвольные темы. У каждой подборки — собственные записи, теги, настройки и история. Не создавать никаких записей автоматически.
- **Три способа создать подборку:** (1) выбрать готовый шаблон, (2) начать с пустой подборки и самостоятельно задать поля, (3) импортировать подборку из JSON.
- **Восемь шаблонов без предустановленных записей:** «Рецепты» (ингредиенты, приготовление, время приготовления, ссылка); «Фильмы и сериалы» (тип, жанр, год, платформа, ссылка); «Игры» (платформа, жанр, ссылка, заметки); «Места и досуг» (адрес, стоимость, ссылка, заметки); «Книги» (автор, жанр, ссылка, заметки); «Идеи и занятия» (категория, необходимые условия, заметки). «Список покупок» (товар, количество, отметка «Куплено», заметки); «Вишлист» (желаемая вещь, ссылка, ориентировочная цена, приоритет, отметка «Приобретено»). Поля из шаблона можно изменить, удалить или дополнить. Шаблоны — только удобные заготовки, не фиксированные типы записей.
- **Покупки и вишлисты:** шаблоны «Список покупок» и «Вишлист» выпущены вместе с «Подборками» в 2.17.0, включая отметки купленных товаров и приобретённых желаний. Передача вишлиста через JSON-файл реализована; более удобный обмен, совместное редактирование и серверная синхронизация остаются отдельными идеями без утверждённой реализации.
- **Общие поля записи:** название; необязательное описание; теги. **Настраиваемые поля подборки:** текст, многострочный текст и ссылка. Поля пользователь создаёт и называет сам. Не делать сложный конструктор форм на старте.
- **Обложки записей (согласовано 15.11.2026):** необязательное изображение для каждой записи — выбор из локального файла или по URL. При отсутствии изображения показывать стандартную иконку. Локальный файл копировать в хранилище AppShelf, изображение по URL скачивать и сохранять локально — обложки должны работать без доступа к исходнику и без интернета. Конкретные правила очистки и экспорта изображений определить при разработке.
- **Просмотр и фильтрация:** ручной просмотр каталога, поиск по названию и нескольким тегам с совпадением всех выбранных тегов; случайный выбор из каталога или результатов фильтра. Кнопка «Другой вариант» только показывает иной результат и не меняет историю. Только подтверждение результата записывает факт и дату действия; текст кнопки подтверждения настраивается для каждой подборки («Приготовили», «Посмотрели», «Поиграли», «Выполнено» и т. п.). Недавно подтверждённые варианты получают меньший шанс повторного выпадения, но не исключаются; шанс постепенно восстанавливается без фиксированного срока. Алгоритм пробуем в таком виде и меняем только по результатам использования.
- **Импорт JSON — два сценария:** создать целую подборку со структурой полей, тегами и записями либо добавить записи в существующую с проверкой совместимости полей. Перед записью показывать предварительный результат импорта; совпадающие записи — пропустить или заменить по выбору пользователя. Допускается JSON, подготовленный внешним ИИ; не добавлять встроенный ИИ, сетевые API, синхронизацию или импорт меню по дням.
- **Размещение и интерфейс:** отдельное окно, открываемое через самостоятельный пункт **«Подборки»** в меню `⋯` AppShelf; не помещать в «Инструменты» и не добавлять кнопку в нижнюю панель. У окна слева список подборок, в центральной области записи выбранной подборки, поиск и теги; справа — подробная карточка случайно выбранного варианта с кнопками «Другой вариант» и подтверждением. Добавление записи и создание подборки — отдельные понятные действия. Согласованные визуальные макеты для кино и игр — ориентир для оформления **самого окна Подборок**, а не изменение навигации главного окна AppShelf.
- **Хранение и резервные копии (согласовано 15.11.2026):** все данные модуля локально в `%APPDATA%\AppShelf\Collections\`: `collections.json` — подборки, записи, дополнительные поля, теги, история; `Images\` — сохранённые копии обложек. Автоматически сохранять изменения. Расширить существующее резервное копирование и восстановление AppShelf, чтобы оно включало данные подборок и изображения. Не перемещать пользовательские данные рядом с EXE, не использовать облако и регистрацию.
- **Фактический статус:** «Подборки» выпущены в 2.17.0: локальная модель, восемь шаблонов, CRUD, настраиваемые поля, фильтры, история, обложки, JSON-импорт/экспорт и ZIP-резервирование. **Открытые вопросы:** очистка неиспользуемых изображений с учётом `.bak`, обмен вишлистами помимо JSON, совместное редактирование и резервирование подарков. Не считать эти идеи согласованными к реализации.

### Идеи обмена вишлистами и резервирования подарков — пока не реализовывать

**Статус:** идеи зафиксированы 17.11.2026; ни один дополнительный вариант обмена или резервирования не утверждён к разработке. Первая версия «Подборок» выпущена в 2.17.0; новый функционал согласовывать отдельно, включая права получателей, сервер и конфиденциальность.

- **Скопировать вишлист в буфер обмена:** удобный структурированный текст для Telegram и других мессенджеров: название, описание, ориентировочная цена, ссылка на товар. Получателю AppShelf не нужен. Без фотографий и без обновлений после отправки.
- **Экспорт в самостоятельный HTML-файл:** красивые карточки с названием, изображениями, ценами, описанием и ссылками на магазин. Локальные обложки по возможности встраивать внутрь HTML, чтобы получателю хватило одного файла. Открывается обычным браузером на ПК или телефоне, без AppShelf, сервера и регистрации; после отправки данные не обновляются. Вариант отложен: по состоянию на 19.11.2026 решение о необходимости HTML-экспорта не принято.
- **Экспорт/импорт JSON:** передавать подборку между пользователями AppShelf с возможностью редактировать собственную копию; JSON-импорт и экспорт реализованы в версии 2.17.0. Не считать импорт синхронизацией; перенос локальных обложек для этого формата решать отдельно.
- **Постоянная веб-ссылка на актуальный вишлист:** получатель открывает живой список в браузере; после изменений автором доступная по той же ссылке версия обновляется. Потребуется отдельное решение по публикации, внешнему хранилищу/серверу, правам доступа и отзыванию ссылки. Не предполагать обязательную регистрацию.
- **Резервирование подарков («Я подарю»):** несколько получателей одного вишлиста видят, что вещь уже зарезервирована, и не покупают дубликаты. Автор вишлиста **не видит, кто что зарезервировал**, чтобы не портить сюрприз; отдельно решить, должен ли он видеть вообще факт резервирования. Нужны безопасная синхронизация отметок между получателями, возможность отменить бронь, защита от двойного резервирования и приватность действий. Простого HTML/JSON-файла для этого недостаточно — вероятно, понадобится общая онлайн-база. **Это самостоятельная будущая функция, не часть ближайшего релиза.**

Общее требование ко всем способам: пользователь сам выбирает, что экспортировать и кому отправлять; не публиковать локальные пути, приватные данные приложения или служебные файлы. Получателю по возможности не должно требоваться AppShelf.

## 2. Открытые расследования

- [ ] **RDP-антипростой: периодическая блокировка Windows — расследование отложено.** В удалённом сеансе может появляться экран блокировки с запросом пароля, хотя AppShelf продолжает отвечать. Проверить срабатывание `DispatcherTimer` раз в 50 секунд, отправку F15 после 40 секунд бездействия, влияние сна, удалённого сеанса и групповых политик Windows. Не считать заранее дефектом AppShelf и не менять код без подтверждённой причины.
- [ ] **Пропущенное напоминание после позднего запуска — расследование отложено.** В одном из наблюдавшихся случаев ежедневное напоминание не показало уведомление при запуске приложения после времени срабатывания; интерфейс уже отображал следующую дату. В 2.13.0 добавлены `pendingAlert` и тесты, но причина этого случая не доказана. Проверить реальную доставку при позднем запуске, запуск из трея, завершение с открытым уведомлением и повторный старт. Не считать инцидент окончательно исправленным без проверки.
